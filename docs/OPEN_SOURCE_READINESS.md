# Open-source repository readiness

## Scope

M11 prepares the repository's public entry points while it remains private. It covers product presentation, architectural explanation, community participation, vulnerability reporting, support expectations, repository metadata, and automated consistency checks. It does not change visibility, enable hosted CI, publish a package or release, create a website, or promise production support.

## Public entry-point contract

The root README must answer, in order:

1. What problem does Quatopsy solve?
2. Who is it for?
3. What can a new evaluator run immediately?
4. What does the output look like and who owns verdicts?
5. Which capabilities are shipped, and where are their safety boundaries?
6. How can someone build, test, contribute, get support, report a vulnerability, and understand the licence?

The canonical release lockup appears above the fold. The architecture image is generated by `scripts/brandkit.py`, recorded in `quatopsy.brand/2`, contains accessible title and description elements, uses no scripts or remote resources, and remains legible when scaled to a narrow README column.

## Community contract

- `CONTRIBUTING.md` defines the development gate, verdict and source-integrity invariants, protocol/rule evidence, adapter provenance, and pull-request expectations.
- `CODE_OF_CONDUCT.md` sets participation and private enforcement expectations.
- `SECURITY.md` routes vulnerabilities to GitHub private vulnerability reporting after public opening, records the current private-repository limitation, and warns against transmitting sensitive telemetry.
- `SUPPORT.md` separates normal issues from vulnerabilities and refuses mission-operations support expectations.
- Structured issue forms collect reproducible behavior, format semantics, provenance, and safety boundaries without inviting operational data.
- The pull-request template requires behavioral evidence, public-contract updates, data/licence review, and the authoritative local CI result.

## Repository metadata contract

`.github/repository-settings.json` is the reviewed source for GitHub About metadata. `scripts/check-community.py` validates its schema, description length, sorted topic syntax, private-visibility boundary, hosted-CI boundary, required community files, README local links, architecture accessibility, and SVG safety.

The approved description is:

> Find, explain, and visualize quaternion attitude failures, then evaluate controller and trajectory candidates locally.

Approved topics are `attitude-control`, `gnc`, `quaternion`, `robotics`, `rust`, `simulation`, `spacecraft`, `trajectory-optimization`, and `visualization`.

No homepage is set until a canonical project site exists. Repository visibility stays private and hosted CI stays disabled until the owner explicitly authorises the separate public-opening change.

The description and nine topics were applied and read back from GitHub on 2026-08-27. The repository remained private, the homepage remained unset, and GitHub Actions was explicitly disabled at repository level.

## Opening handoff

After M11, the public-opening increment should verify the M11 files on `master`, change visibility, immediately enable private vulnerability reporting, enable the minimal hosted form of the existing local gate, inspect the live public README and social preview, verify issue forms and security links from a logged-out context, and then re-evaluate the publication checklist. GitHub exposes public vulnerability reporting only after the repository is public, so visibility and that reporting control must be treated as one fail-closed sequence. The increment must not silently add package publication, signing, a website, or support commitments.
